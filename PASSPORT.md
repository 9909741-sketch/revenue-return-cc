--- БЛОК 1. ПРОДУКТ ---
ДЛЯ КОГО (первичный сегмент, конкретно): операторы контакт-центра розничной сети напольных покрытий и сантехники (компания «Баусервис», бренд Laparet), обрабатывающие 100+ обращений в день через Битрикс24.
JTBD: когда сделка клиента отменяется сотрудником торговой точки или тёплый лид закрывается без результата, я (оператор КЦ) хочу увидеть эту сделку в своём задачнике с приоритетом, чтобы позвонить клиенту и вернуть сделку в продажу до того, как она потеряна окончательно.
ГЛАВНАЯ БОЛЬ (с измеримым критерием): часть выручки, переданной на торговые точки, не доходит до продажи из-за необоснованных отмен и «зависших» тёплых лидов, и это никем не отслеживается системно. Измеримый критерий: доля некорректных отмен и доля тёплых лидов без повторного касания — конкретные проценты неизвестны до анализа фактической выгрузки (Допущение: подтверждается на первой загрузке и 4-недельном пилоте, см. RISKS.md, пункт 2).
АЛЬТЕРНАТИВЫ СЕЙЧАС (и почему уйдут): стандартные отчёты Битрикс24 — показывают факт отмены, но не организуют повторный обзвон и не хранят историю отработки, уйдут при появлении рабочего задачника; ручная выгрузка в Excel у руководителя КЦ — трудоёмка и не переживает смену сотрудника, уйдёт при автоматизации; «никак не проверяется» — уйдёт, если пилот подтвердит гипотезу о доле некорректных отмен.
MVP-ДЕЙСТВИЕ (одно): оператор КЦ открывает задачу по отменённой сделке или тёплому лиду, звонит клиенту и фиксирует результат звонка, который автоматически обновляет статус и метрики.
КРИТЕРИЙ УСПЕХА ПЕРВОЙ СЕССИИ: оператор берёт в работу минимум одну задачу из задачника, звонит клиенту и закрывает задачу с проставленным статусом и обязательным комментарием.

--- БЛОК 2. SCOPE ---
ФУНКЦИИ MVP (не больше 5, для каждой: вход → выход → поведение при некорректном вводе):
1. Импорт выгрузки Б24 (XLSX/CSV) → сделки (upsert по deal_id), автосоздание задач для новых отмен и тёплых лидов → строки без обязательных полей идут в список «ошибки загрузки» и не создают задач; сделки без суммы — в список «требует уточнения суммы», исключены из денежных метрик.
2. Задачник «Отмены»: действие оператора (взять в работу / зафиксировать звонок / закрыть) → обновлённый статус задачи, запись в touches → закрытие без обязательного комментария блокируется с явной ошибкой.
3. Задачник «Тёплые лиды»: действие оператора и график касаний (3/7/14/30 дней) → обновлённый статус, запись в touches, авто-закрытие после 4-го касания без результата с обязательной причиной W01–W08 → попытка закрыть без причины блокируется.
4. Отчётность: выбор периода и разреза (оператор/ТТ/сотрудник ТТ/товарная группа) → таблицы метрик обоих модулей, сравнение с предыдущим периодом, экспорт CSV → пустой период/нет данных — экран «нет данных за период» с подсказкой загрузить выгрузку.
5. Пользователи и роли (админка): данные нового пользователя от администратора → учётная запись с ролью и (для роли «Руководитель ТТ») привязкой к точке → дублирующийся email — ошибка с указанием существующей записи.
ФАЗА 2: живая интеграция с Б24 REST API вместо ручной выгрузки; Telegram-уведомления операторам о новых задачах и просрочке SLA; автоэскалация просроченных задач руководителю КЦ; отчёты по расписанию на email; настраиваемый справочник товарных групп.
ФАЗА 3: сверка с КП 1С; скоринг перспективности реанимации по истории причин и оператора; контрольная группа для замера чистого эффекта (A/B); встроенная телефония (клик-ту-колл).
АНТИСКОП (≥5, каждый с причиной: не сейчас / никогда / есть готовое решение):
1. Прямая двусторонняя интеграция с Б24 через REST API — не сейчас: для одного автономного прогона надёжнее ручная/периодическая загрузка выгрузки.
2. Мотивация и депремирование сотрудников ТТ внутри инструмента — никогда: инструмент фиксирует факты, решения по мотивации — зона HR и юриста.
3. Мобильное приложение (iOS/Android) — никогда: операторы КЦ работают за компьютером, достаточно адаптивного веба.
4. Встроенная телефония, клик-ту-колл, запись звонков — не сейчас: оператор звонит с текущей телефонии компании, инструмент только фиксирует результат.
5. Интеграция с КП 1С — не сейчас: единственный источник данных на MVP — выгрузка Б24, сверка добавится в фазе 3.
6. Онлайн-оплата и платёжный контур — есть готовое решение: оплата идёт через существующие кассы компании, инструмент платежей не проводит.
7. SMS-рассылки клиентам — не сейчас: первый канал возврата — звонок оператора, автоматические каналы добавляются после пилота.

--- БЛОК 12. КРИТЕРИИ ПРИЁМКИ ---
1. Загрузка тестового XLSX с 10 сделками создаёт записи и задачи в обоих задачниках.
2. Повторная загрузка того же файла не создаёт дублей — общее число сделок не меняется.
3. Сделка без суммы попадает в список «требует уточнения суммы» и не учитывается в денежных метриках отчёта.
4. Закрытие задачи без комментария блокируется с понятной ошибкой.
5. Оператор видит в задачнике только свои задачи; прямой запрос к API с чужим task_id не отдаёт данные.
6. Руководитель ТТ видит отчётность только по своей точке.
7. Переход задачи в REPASS или WON доступен только после минимум одного зафиксированного касания.
8. Тёплый лид без результата после 4-го касания автоматически закрывается в NO_RESULT с обязательной причиной W01–W08.
9. Приложение поднимается в Replit командой из блока 3 и слушает 0.0.0.0 на порту из PORT.
10. Отчёт по периоду и разрезу выгружается в CSV с теми же цифрами, что на экране.
11. Администратор может создать пользователя, назначить роль и сбросить пароль существующему.
12. Демо-данные видны сразу после первого запуска без ручной загрузки выгрузки.
