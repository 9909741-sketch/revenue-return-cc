## 2026-09-25 — Этап 0. Ограничения окружения

**Решение**: в песочнице, где выполняется сборка, отсутствуют `node`, `npm` и `git` (проверено — команды не распознаются, стандартные пути установки пусты, `winget`/`choco` тоже недоступны). Черновой список правил прямо запрещает установку глобальных системных пакетов, поэтому Node.js/npm/Git не устанавливались.

**Следствие**:
- Весь код написан вручную, без возможности запустить `npm install`, `tsc`, `npm run dev/build/start`, тесты или интерпретатор.
- Git-репозиторий и чекпоинт-коммиты по этапам, требуемые BUILD_PROMPT.md, физически невозможны без бинарника `git`. Вместо коммитов прогресс по этапам фиксируется записями в этом файле и чекбоксами в `docs/PLAN.md`. Пользователь может сам выполнить `git init` и `git add -A && git commit` на машине, где git установлен (команды перечислены в docs/RUN.md).
- В `docs/ACCEPTANCE.md` состояние «проверено вживую» честно не проставлено там, где нужен реальный запуск Node.js/PostgreSQL — вместо этого «написано, не проверено» с пояснением.

**Почему так, а не иначе**: правило 5 требует не останавливать работу целиком при неудаче этапа, а зафиксировать причину и двигаться дальше. Отсутствие рантайма — это не ошибка в коде, а ограничение среды выполнения; самый простой рабочий вариант — довести код до состояния «готов к первому запуску на машине с Node.js» и подробно описать эти шаги в docs/RUN.md.

## 2026-09-25 — Этап 0. Выбор версий пакетов

Проверено через веб-поиск (не по памяти), фактические версии на 2026-09-25:

- Node.js: активная LTS-ветка — 24.x (Node 22 — предыдущая LTS в режиме Maintenance). В `engines` указано `>=22`.
- Vite 8.x (актуальный мажор, вышел в марте 2026).
- Tailwind CSS 4.x — с версии 4.0 конфигурация CSS-first (`@import "tailwindcss"` + `@theme` в CSS вместо `tailwind.config.js` с `content`/`theme.extend`), отдельный плагин `@tailwindcss/vite`. Использован именно этот способ подключения, а не устаревший PostCSS-конфиг из документации v3.
- React 19.x, react-router-dom 7.x.
- Express 5.x — актуальный стабильный мажор (Express 4 в Maintenance, EOL не ранее октября 2026). Учтено ломающее изменение роутинга: в Express 5 (path-to-regexp v8) голый `app.get('*', ...)` больше не работает — для отдачи SPA-страницы на все не-API маршруты использован `app.use()` без пути вместо шаблона `'*'`.
- Пакет `xlsx` (SheetJS) официально снят с реестра npm (последняя версия там — устаревшая 0.18.5 с известными уязвимостями). Официальная рекомендация проекта — ставить пакет с их собственного CDN: `xlsx: "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz"` в package.json. Использован именно этот способ, а не `npm install xlsx`.
- `multer` — использована актуальная линейка 2.x (в 2.2.0 закрыты DoS-уязвимости версий до 2.2.0, актуальна 2.4.x).
- Пароли хэшируются `bcryptjs` (чистый JS), а не `bcrypt` — исключает риск ошибок нативной компиляции при установке в незнакомом окружении (в том числе в этой песочнице и потенциально на Replit).

Так как `npm install` в этой сессии выполнить нельзя, фактически зафиксированные в package-lock.json версии появятся только после первого `npm install` пользователем — тогда стоит перепроверить эту запись.

## 2026-09-25 — Этап 0. Архитектурные решения

1. **Монорепозиторий на npm workspaces**: `client/` (Vite+React) и `server/` (Express) — два пакета в одном репозитории, корневой package.json оркестрирует команды `dev`/`build`/`start` из блока 3 паспорта.
2. **Без ORM**: доступ к PostgreSQL — через `pg` (Pool) и обычный SQL в файлах миграций (`server/src/db/migrations`). Причина: меньше версионных сюрпризов без возможности прогнать миграции локально; SQL проще проверить чтением, чем угадать API конкретной версии ORM.
3. **Миграции и демо-данные применяются автоматически при старте сервера** (перед `listen`), а не отдельной командой — потому что `.replit` запускает только `npm start`, отдельного шага миграции в деплое нет.
4. **UI-кит без CLI shadcn/ui**: сама shadcn/ui — это CLI, который копирует исходники компонентов через `npx shadcn add ...`; выполнить его без npm нельзя. Вместо этого вручную написан минимальный набор компонентов (`client/src/components/ui`) в той же стилистике (Tailwind-классы, тот же визуальный язык), без будущей миграции на Radix — если понадобится, легко заменить.
5. **Сессии — `express-session` с хранилищем в памяти процесса** (не Postgres-backed store). Для MVP с автономным одним процессом это самый простой рабочий вариант; побочный эффект — при рестарте сервера все пользователи должны войти заново (сами данные в БД не теряются). Если это неприемлемо — заменить на `connect-pg-simple` в фазе 2.
6. **UUID генерируются в PostgreSQL** через `gen_random_uuid()` (расширение `pgcrypto`), не в коде — меньше кода, одна точка генерации ключей.
7. **touches.result_code**: в SPEC этот код не описан отдельным словарём (только справочники R01–R10 для отмен и W01–W08 для тёплых лидов). Решено: при промежуточном звонке (без закрытия) result_code — один из кодов исхода звонка `ANSWERED` / `NO_ANSWER` / `CALLBACK` (телефонный исход, не бизнес-причина); при закрытии в финальный статус result_code — код причины из R01–R10 или W01–W08 (тот же, что ушёл в `deals.cancel_reason_code` либо в причину закрытия тёплого лида). Единый словарь кодов вынесен в `server/src/domain/statusCodes.ts` и переиспользуется на фронтенде через идентичные строковые константы.
8. **FK на users.email у deals/tasks/touches не оформлены как жёсткие внешние ключи в БД**, а проверяются на уровне приложения (LEFT JOIN при отображении). Причина: выгрузка Б24 может содержать оператора или сотрудника ТТ, для которого ещё не заведена учётная запись — жёсткий FK уронил бы весь импорт. Это самостоятельное решение, при необходимости разворачивается в отдельную задачу «сопоставление email выгрузки со справочником пользователей».

## 2026-09-25 — Этапы 3–4. Уточнение переходов статусов и разреза отчётности «оператор»

- В docs/SPEC.md, раздел 4.1 текстом написано «NO_ANSWER → WIP, CANCEL_OK или DONE_KC», а mermaid-диаграмма в том же разделе не содержит перехода `WIP --> NO_ANSWER` обратно. Из двух представлений одного раздела выбрана диаграмма как более точная формальная спецификация переходов — реализовано без обратного перехода WIP→NO_ANSWER (`server/src/domain/statusCodes.ts`).
- Тёплый лид: если оператор фиксирует звонок прямо из статуса NEW, не нажимая отдельно «Взять в работу», действие неявно считается переводом в WIP в момент этого звонка — иначе переходы, доступные только из WIP (в т.ч. обязательное автозакрытие после 4-го касания), были бы недостижимы для лида, который ни разу явно не «брали в работу» (`server/src/services/taskService.ts`, переменная `effectiveStatus`).
- Разрез отчётности «Оператор КЦ» считается по `deals.kc_operator_email` (владелец сделки из выгрузки), а не по `tasks.assigned_operator_email` конкретной задачи — иначе сделки без задачи (например, обычная сделка без отмены) не участвовали бы в знаменателе «передано на ТТ» ни в одной группе, искажая долю отмен по оператору. Поскольку переназначение задач между операторами не реализовано (см. ниже), оба значения всегда совпадают, так что упрощение ничего не теряет.

## 2026-09-25 — Повторная проверка окружения и правка TS2345 в taskRoutes.ts

**Задача**: устранить ошибку сборки TS2345 в `server/src/routes/taskRoutes.ts` — в Express 5
`req.params.id` типизируется как `string | string[]`, а `getTaskWithTouches`, `takeTask` и
`recordTouch` (server/src/services/taskService.ts) принимают строго `string`.

**Правка**: во всех трёх местах вызов обёрнут в `String(req.params.id)`:
- `getTaskWithTouches(actor, String(req.params.id))`
- `takeTask(actor, String(req.params.id))`
- `recordTouch(actor, String(req.params.id), {...})`

`String(...)` детерминированно возвращает `string` независимо от того, разрешается ли тип
параметра Express в `string` или в `string | string[]` — это устраняет несоответствие типов
без изменения поведения на корректных запросах (Express формирует `params.id` из литерала пути
`/:id`, реальное значение всегда одна строка; двойного значения быть не может по построению
маршрута, `String()` — чисто типовая, а не поведенческая правка).

**Повторная проверка окружения**: по просьбе пользователя проверил ещё раз, доступны ли теперь
`node`/`npm` в этой песочнице — не появились. Проверено несколькими независимыми способами:
команды `node --version`/`npm --version` не распознаются; нет ни в одном из стандартных путей
установки (`Program Files\nodejs`, `AppData\Local\Programs\nodejs`, `AppData\Roaming\npm` и т.п.);
нет записей `node`/`npm` ни в машинном, ни в пользовательском PATH (проверено напрямую через
`[System.Environment]::GetEnvironmentVariable('Path', ...)`); полный рекурсивный поиск файла
`node.exe` по всему диску C:\ (глубина 4) не нашёл ни одной копии. Таким образом, `npm install`
и `npm run build` в этой сессии выполнить физически невозможно — не только по причине домена
`cdn.sheetjs.com` (эта частная проверка вообще не была достигнута, так как отсутствует сам
исполняемый файл `npm`), а из-за отсутствия самого рантайма Node.js. Это более фундаментальное
ограничение, чем ожидалось в задаче, и оно указано явно, а не подменено похожим, но более узким
объяснением.

**Что сделано вместо реального прогона**: правка вычитана вручную построчно, сопоставлена с
сигнатурами `taskService.ts` (`taskId: string` во всех трёх функциях) — по построению корректна.
Строка «Сборка проходит без ошибок» в docs/ACCEPTANCE.md оставлена как «не сделано» с этим же
объяснением, а не помечена «проверено вживую» — фабриковать положительный результат
несуществующего прогона недопустимо.
