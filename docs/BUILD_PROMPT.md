## Что строим

Веб-инструмент для контакт-центра розничной сети напольных покрытий и сантехники (компания «Баусервис», бренд Laparet). Оператор КЦ обрабатывает два задачника на общем ядре данных: отменённые сделки, переданные на торговые точки, и «зависшие» тёплые лиды. Единственный источник данных — периодическая ручная выгрузка сделок из Битрикс24 (XLSX/CSV). Оператор звонит клиенту и фиксирует результат — статус обновляется, метрики пересчитываются. Руководители и администратор видят отчётность и управляют пользователями.

## Функции MVP

Полные формулировки вход → выход → поведение при некорректном вводе — в PASSPORT.md, блок 2. Кратко:

1. **Импорт выгрузки Б24 (XLSX/CSV)** → сделки (upsert по deal_id), автосоздание задач для новых отмен и тёплых лидов. Строки без обязательных полей → «ошибки загрузки», не создают задач. Сделки без суммы → «требует уточнения суммы», исключены из денежных метрик. Повторная загрузка того же файла не создаёт дублей (критерий приёмки №2).
2. **Задачник «Отмены»**: взять в работу / зафиксировать звонок / закрыть → обновлённый статус, запись в touches. Закрытие без обязательного комментария блокируется явной ошибкой.
3. **Задачник «Тёплые лиды»**: действие оператора + график касаний (3/7/14/30 дней) → обновлённый статус, запись в touches, авто-закрытие после 4-го касания без результата с обязательной причиной W01–W08.
4. **Отчётность**: период + разрез (оператор/ТТ/сотрудник ТТ/товарная группа) → таблицы метрик обоих модулей (формулы — docs/SPEC.md, раздел 8), сравнение с предыдущим периодом, экспорт CSV. Пустой период → «нет данных за период» с подсказкой загрузить выгрузку.
5. **Пользователи и роли (админка)**: данные нового пользователя от администратора → учётная запись с ролью и (для «Руководитель ТТ») привязкой к точке. Дублирующийся email → ошибка с указанием существующей записи.

## Модель данных

Полная таблица сущностей и полей — PASSPORT.md, блок 5 (сущности `deals`, `tasks`, `touches`, `users`, `import_batches`, `audit_log`).

Стабильные ключи: `deal_id` (ID сделки Б24) для сделок и задач, `email` для пользователей. Не полагайся на идентификаторы, сгенерированные во время локальной разработки: после развёртывания они не совпадут.

Удаление: мягкое (флаг active/deleted_at) для deals, tasks, users; audit_log и touches не удаляются.

Демо-данные для первого запуска: 5 демо-отмен и 5 демо-тёплых лидов с вымышленными телефонами/именами, 3 демо-пользователя (оператор, руководитель КЦ, администратор) — создаются автоматически при первом запуске, без ручной загрузки выгрузки (критерий приёмки №12).

## Роли и доступ

Матрица прав — PASSPORT.md, блок 6 / docs/SPEC.md, раздел 2 (дословно, единый источник).

Проверка прав выполняется на сервере до выполнения запроса, а не фильтрацией в интерфейсе.

Авторизация: вход по email и паролю; самостоятельная регистрация отключена, учётные записи создаёт администратор.

Lockout-сценарий: администратор сбрасывает пароль оператору из админ-панели (временный пароль показывается один раз). Если единственный администратор потерял доступ — восстановление через переменную окружения `ADMIN_RECOVERY_CODE`: защищённый служебный эндпоинт при точном совпадении кода из Secrets создаёт нового администратора или сбрасывает пароль существующего.

Нет. Классификация «тёплый лид» приходит готовым полем из выгрузки Б24, дополнительная языковая модель не требуется в этом прогоне.

## Статусные модели

Полные диаграммы переходов (mermaid) и правила — docs/SPEC.md, раздел 4. Коды статусов и переходы используй дословно, они входят в критерии приёмки №7 и №8:

- Модуль «Отмены»: NEW → WIP или NO_ANSWER; NO_ANSWER → WIP, CANCEL_OK или DONE_KC; только REPASS → WON; переход в REPASS/WON доступен только после минимум одного зафиксированного касания; закрытие в финальный статус требует обязательного комментария.
- Модуль «Тёплые лиды»: NEW → WIP → PASSED_TT / NO_RESULT / WON; после 4-го касания без результата — автозакрытие в NO_RESULT с обязательной причиной W01–W08. Если тёплый лид передан на ТТ (PASSED_TT) и там отменяется — та же сделка (тот же deal_id) автоматически появляется в задачнике «Отмены», отдельная сущность не создаётся.

Формула приоритета задачи (сортировка по убыванию): сумма сделки — 50%, давность события — 30%, признак некорректной причины (R04, R06, R07, R10) — 20%. Задачи старше 14 дней уходят в конец очереди, но не удаляются.

SLA: первый звонок по отмене — не позднее 24 часов с момента появления в выгрузке; просроченная задача подсвечивается в списке (автоматическая эскалация руководителю — вне MVP).
